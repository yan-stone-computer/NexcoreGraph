## 1. 当前仓库的主体地位

本作品以当前仓库 `NexcoreGraph` 为唯一产品主干。鸿蒙端、Node 后端、GraphRAG、数字孪生、训练方案、同步中转和评测脚本均在本仓库内实现。

用户提供的 GitHub 仓库只作为以下来源使用：

- 可复用设计模式；
- 可替换协议和模块边界；
- MIT 许可的参考实现；
- 架构图、README 与评测材料的表达方式。

不直接复制整个外部项目，不引入未审计的运行时依赖，不把候选项目写成已完成集成。

## 3. 哪些已经实际进入本作品

### 3.1 ToolGuard 式审批

本作品中的 AI 写操作不是“模型说一句就改库”：

1. 工具必须在白名单；
2. 目标对象、数量与参数先解析；
3. UI 生成确认卡；
4. 用户确认后执行；
5. 幂等键阻止重复落地；
6. 数量、药品每日用量和策略结果进入本地日志。

这与 `NexcoreToolGuard` 的核心思路一致：审批表达的是“这一次动作”，不是永久放开某类工具。

### 3.2 Memory / GraphRAG 式证据

家庭资源图谱由代码构建，模型只解释结果：

- 物品实例；
- 所属资源域；
- 库位；
- 临期、余量、维护关系；
- GraphRAG 路径；
- 数字证据与来源行。

回答必须能说明“依据了哪些资源事实”，而不是只给一句看似合理的建议。

### 3.3 Vision 式证据分层

扫码和视觉识别保持职责分离：

- 扫码：精确识别码；
- 视觉：名称、类别、数量、位置等候选字段；
- 用户：最终确认；
- 多物品识别时不猜测条码归属。

这与 `NexcoreVision` 的“文字事实与视觉语义分开保留”原则一致。

## 4. 后续可直接适配的模块

### 4.1 上下文治理

当药品说明、保修单、训练资料和家庭历史同时进入模型时，可按 `nexcore-context-governor` 的顺序处理：

```text
固定系统约束
  → 当前问题
  → 资源证据
  → 历史摘要
  → 低优先级注入
```

超限时优先删低价值历史，保留药品安全边界、资源数字和用户确认约束。

### 4.2 文档导入

`NexcoreFileRead` 可接入：

- 药品说明书；
- 健身器材安装与保养手册；
- 工具保修卡；
- 家庭资源盘点表。

文档解析结果必须继续走字段预览和用户确认，不直接改库存。

## 5. 模型平台适配层

### 5.1 支持形态

后端使用 OpenAI-compatible 协议作为统一适配面，内置：

| 平台 | 默认协议 |
|---|---|
| Agnes AI | `OpenAI-compatible /v1/chat/completions` |
| DeepSeek | OpenAI-compatible |
| 通义千问 DashScope | OpenAI-compatible |
| 智谱 GLM | OpenAI-compatible |
| Moonshot Kimi | OpenAI-compatible |
| OpenAI | OpenAI-compatible |
| Ollama | 本地 OpenAI-compatible |
| 自定义平台 | 任意合法 HTTP/HTTPS Base URL |

### 5.2 可配置项

- 平台预设；
- Base URL；
- 主模型；
- 备用模型；
- 视觉模型链；
- 超时；
- RPM；
- 视觉硬预算；
- API Key；
- 配置管理员令牌。

### 5.3 安全边界

- API Key 不进入鸿蒙端持久化；
- 端侧只显示服务端返回的脱敏尾号；
- 修改配置必须携带 `AI_CONFIG_ADMIN_TOKEN`；
- 运行时配置保存到后端 `.ai-config.json`，该文件已 gitignore；
- 非本机部署修改配置必须使用 HTTPS；
- 模型不可用时，本地快答、规则、图谱、数字孪生和训练计划仍能工作。

## 6. 商业价值

### 6.1 用户价值

- 家庭不必在食品、药品、器材和工具之间切换四套工具；
- 药品余量、训练计划和工具维护都用同一套家庭事实；
- 模型平台可替换，避免被单一厂商绑定；
- 局域网/私有部署适合对隐私敏感的家庭和机构。

### 6.2 商业模式候选

| 模式 | 内容 | 前提 |
|---|---|---|
| 家庭基础版 | 本地库存、资源图谱、数字孪生、训练计划 | 免费或低价获客 |
| 家庭 Pro | 多成员协作、跨端同步、高级评测与历史分析 | 订阅 |
| BYOK | 用户自带模型 Key，平台不承担推理成本 | OpenAI-compatible 适配 |
| 私有部署 | 养老、家政、校园和社区家庭服务 | HTTPS、权限和运维 |
| 场景模板 | 老人照护、健身家庭、维修爱好者、宿舍 | 模板审核与专业边界 |

## 7. 获客与推广

1. 用本地可用的数字孪生和训练计划做首屏演示，不依赖模型 Key；
2. 开放 BYOK，技术用户可以直接接入自己已有的模型账号；
3. 发布药品、健身、工具三类体验模板，降低首次建库成本；
4. 与校园、家政、社区养老服务做小范围试点；
5. 用 GuardrailBench、确认卡和证据链做信任背书，而不是只讲模型参数；
6. 在 Git 仓库公开适配协议、第三方许可证和测试报告，方便渠道方复核。
