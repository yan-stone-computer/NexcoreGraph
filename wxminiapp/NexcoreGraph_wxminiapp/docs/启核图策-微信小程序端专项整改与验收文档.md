## 4. 小程序端开发方案

### 4.1 M-1 技术选型与工程结构（按真工程定稿）

**选型结论：保留现有 Taro 4.1.9 + React 18 + TypeScript 工程，不迁移原生。**

| 方案 | 评估 | 结论 |
|---|---|---|
| **Taro 4.1.9 + React 18 + TS（现有）** | 已实现 10 页 + 6 组件 + zustand + 服务层；本次实测构建通过（27.5s）；主包 0.55MB（远低于 2MB）；还能顺带产出 H5 版复用 Web 资产 | ✅ **保留** |
| 原生小程序 + Skyline | 平台能力最直接，但需重写全部页面与组件，工期与返工风险高，而当前并不存在性能问题 | ❌ 不迁移（除非出现 Skyline 独占需求） |
| uni-app | 生态广但需重写，流式处理更绕 | ❌ 不采用 |

保留 Taro 的前提下，整改需补三项原生能力调用（Taro 均可直调）：`Taro.request({ enableChunked: true })` 分段流式、`Taro.requestSubscribeMessage` 订阅消息、`Taro.getPrivacySetting` / `onNeedPrivacyAuthorization` 隐私授权。

### 4.4 接口契约（与 Web/鸿蒙共用）

```http
POST /api/auth/login        { phone, code } 或 { code(微信) }  -> { user, family, role, token }
POST /api/ai/chat           { question, intent?, evidence?, stream? }  -> text | chunked 流
POST /api/ai/vision         upload file（multipart）  -> { items:[{name,category,qty,unit,pos,expDays,price,priceSrc,confidence}] }
GET  /api/knowledge         ?q=&type=food|recipe|rule  -> { hits:[{title,text,src,url,score}] }
GET  /api/ai/usage          ?familyId=&range=7d  -> { calls, byIntent{}, p95, savedByFastPath }
GET/POST /api/families*     （成员、邀请码）
POST /api/sync/upload       { familyId, baseVersion, force, payload }  -> 409=冲突
POST /api/notify/subscribe  { familyId, templateId, topic }  （订阅消息登记）
```

**域名要求**：小程序 `request` / `uploadFile` 域名必须在微信后台配置白名单（HTTPS + 备案域名）。开发期可勾选"不校验合法域名"。

### 4.5 M-3 AI 对话与流式输出（小程序难点）

小程序不支持 `EventSource`，可行方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **分段传输（采用）** | `wx.request({ enableChunked: true })` + `onChunkReceived` 逐块拼接渲染（后端返回 `Transfer-Encoding: chunked` 的纯文本或 `data:` 行） | 延迟最低，微信基础库 ≥2.20.2 支持 |
| 轮询（降级） | 发起任务 → 拿 `taskId` → 每 800ms `GET /api/ai/chat/result?taskId=` | 兼容性最好，延迟高 |
| 一次性返回（兜底） | 等完整文本返回 | 最稳，无"打字机"效果 |

**实现要点**：`utils/aiClient.ts` 封装三种模式，按基础库版本与后端能力自动选择；保留"停止生成"（`wx.abort`/置标记位）；每轮记录 `{intent, route, model, ms}` 到本地并上报 `usage`。

**快答优先（省调用 + 秒回）**：复用鸿蒙端意图表 —— greet / qty / where / expiry 四类由本地规则 + 缓存数据直接回答（0 次模型），其余走网关。目标：快答命中率 ≥60%。

### 4.6 M-4 Agent 工具链路

工具与规则与 Web 端完全一致（`adjust` / `shopping_add` / `plan_create` / `plan_execute`），差异只在交互形态：

| 环节 | 小程序实现 |
|---|---|
| 预览 | 对话气泡内嵌确认卡（原值 → 新值 + "确认/取消"按钮） |
| 确认 | `wx.showModal` 二次确认（写操作必须） |
| 生效 | 调用后端接口 → 刷新缓存 → `wx.showToast('已更新')` |
| 撤销 | 气泡上"撤销"按钮，5 分钟内可撤销（后端保留操作 id） |
| 红线 | 单请求 ≤2 次模型调用；名称/数量校验；不合法输出当普通文本渲染 |
